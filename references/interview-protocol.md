# 逐题访谈协议

本文件规定 `enterprise-ai-self-check` 的问题顺序。只在需要时读取对应身份分支；不要把整份问题库一次性发给用户。

## A. 通用状态机

每一题采用固定状态：

`提问 → 初答 → 拷问 → 完善回答 → 记录最终答 → 下一题`

每题的记录格式：

```markdown
### Q{{NUMBER}}｜{{DIMENSION}}

**问题**：{{QUESTION}}

**初答**：{{INITIAL_ANSWER}}

**拷问焦点**：
1. {{GRILL_POINT}}

**完善回答**：{{REFINED_ANSWER_OR_维持原答}}

**记录判断**：{{FACT / JUDGMENT / 待会议补充}}
```

### 固定身份题 I-01

> 你今天以什么身份参与这次企业 AI 自查？请选择并说明：老板 / 总经办、部门负责人（请注明部门）、顾问 / 服务商、其他。

拷问焦点：是否说明了职务、决策权限和了解范围；如果不是老板，哪些结论必须带回会议确认。

### 固定企业卡片题 I-02

> 请用一句话介绍你所在的企业 / 服务对象：行业、主营业务、团队大致规模。

拷问焦点：是否说清公司靠什么收入；“团队”是全公司、当前部门还是外包协作团队；缺失信息由谁确认。

---

## B. 老板 / 总经办路径

适合拥有跨部门视角和最终决策权的使用者。顺序不可跳到优先事项；部门题仅对与当前问题有关的部门逐个进行。

| 编号 | 维度 | 每次只问这一题 | 拷问关注点 |
| --- | --- | --- | --- |
| B-01 | 企业背景 | 未来 3–6 个月，公司最想改善的一个业务结果是什么？ | 结果是否是业务结果而非“用 AI”“提效”；改善后谁会看到什么变化。 |
| B-02 | 企业背景 | 请讲一件最近半年真实发生、最影响这个结果的事。 | 发生时间、涉及谁、具体后果；不能只写“协同差”。 |
| B-03 | 企业背景 | 先不讨论平台、系统、AI 或预算：如果接下来三个月只能先理顺一件由人完成的工作，你最想动哪一件？ | 与 B-01 的关系；是否只是某个人抱怨；能否写出起点、动作、接收方和业务结果。 |
| B-04 | 流程自查 | 请按实际顺序写出与这件事相关的一条业务链，从开始到结束。 | 谁发起、何时交接、交接什么信息或文件；不要只写“销售流程”。 |
| B-05 | 流程自查 | 这条链最常卡在哪一步？ | 频率、等待或返工后果、谁本应接住；判断是“点”还是“线”。 |
| B-06 | 流程自查 | 在讨论 AI 前，这个断点最需要先讲清的流程、责任或资料基础是什么？ | 是已知事实还是猜测；谁有权定标准；为什么现在没做到。 |
| B-07 | 部门盘点 | 这条业务链涉及哪些部门和负责人？请只列部门与负责人。 | 是否遗漏上下游或最终验收方；哪些部门只是被影响、哪些真正负责。 |
| B-08{{DEPT}} | 部门盘点 | 针对 {{DEPT}}，请说一个与这条链直接相关、每周反复发生的工作场景。 | 具体动作、频率、输入 / 输出、与其他部门的交接；避免列职能名称。 |
| B-09 | 部门盘点 | 从前面事实中，列出 3 个值得讨论的候选工作内容；每项必须写成“起点 → 人的动作与交接 → 接收方 → 结果”。 | 每项是否不依赖新系统也成立；禁止写“平台 / 系统 / 开发 / AI / 自动化 / 全面数字化”。 |
| B-10 | 优先事项 | 请只选其中 1 项业务工作，按高频、痛苦、可衡量、风险可控各打 0–5 分并说明。 | 四项分数是否有事实依据；风险是否包含对外承诺、资金、合同或隐私；不得给“系统方案”打分。 |
| B-11 | 优先事项 | 作为老板，你最终希望带进会议拍板的优先工作是什么？请按“起点 → 交接工作 → 接收方 → 业务结果”表述。 | 它解决哪件业务事；为何不是另两项；共同牵头人和最终拍板人是否明确；不能出现实现手段。 |

如果 B-07 中列出 N 个相关部门，则顺序执行 N 次 `B-08{{DEPT}}`。默认关键部门为总经办、人事行政培训、财务、销售、项目交付；只问与当前业务链直接相关的部门。技术、市场推广、采购等按实际加入。

## C. 部门负责人路径

目标是产出一份部门事实稿，带回老板和上下游负责人会议讨论。不要声称已完成企业最终优先事项。

| 编号 | 维度 | 每次只问这一题 | 拷问关注点 |
| --- | --- | --- | --- |
| D-01 | 部门边界 | 你负责哪个部门？你对哪一段业务结果负责？ | 责任范围是否清楚；哪些结果要与其他部门共同负责。 |
| D-02 | 部门盘点 | 请说一个你部门每周反复发生、且最占精力的真实工作场景。 | 具体动作、频率、参与人；不要只列“项目管理”。 |
| D-03 | 真实事件 | 最近一次这个场景卡住或返工是什么时候？发生了什么？ | 谁等谁、缺什么、拖了多久、造成什么后果。 |
| D-04 | 流程自查 | 这个场景的上游是谁、你交给谁？ | 输入和输出是否具体；实际交接与制度交接是否一致。 |
| D-05 | 责任基础 | 你认为最该先讲清的一条责任、规则或资料标准是什么？ | 谁能拍板、目前为什么未执行、是否已存在但无人验收。 |
| D-06 | 候选事项 | 请把它写成一个“起点 → 人的动作与交接 → 接收方 → 结果”的候选工作内容。 | 范围是否太大；不含平台、系统、AI、开发等手段词；能否被管理层判断高频、痛苦、可衡量、风险可控。 |
| D-07 | 会议准备 | 这件事需要哪几位负责人在会上共同确认？ | 缺谁会无法决策；你希望老板拍板什么。 |

结束时只给出“部门建议优先事项”和“待管理层确认项”，不替企业选择全公司优先事项。

## D. 顾问 / 服务商路径

顾问以客户事实为中心，必须在每条回答前记录信息来源。若客户尚未提供，标为待访谈。

| 编号 | 维度 | 每次只问这一题 | 拷问关注点 |
| --- | --- | --- | --- |
| C-01 | 委托边界 | 这次复盘的客户是谁？谁将参加并拥有最终拍板权？ | 是否已有老板 / 总经办；顾问是否误把对接人当决策人。 |
| C-02 | 业务背景 | 客户现在最希望改善的一个业务结果是什么？请注明信息来自谁。 | 是客户原话、顾问判断还是待验证；结果能否在 3–6 个月内观察。 |
| C-03 | 真实事件 | 客户讲过的哪件真实业务事件最能说明问题？ | 时间、角色、后果、证据来源；避免顾问归纳替代事实。 |
| C-04 | 流程访谈 | 还需要请哪位客户负责人还原哪一段业务链？ | 具体部门、具体链路、为什么该人掌握事实。 |
| C-05 | 会议设计 | 这场会议最需要客户拍板的一项优先事项是什么？ | 顾问建议与客户决策的边界；仍不能提前设计工具方案。 |

完成后输出访谈缺口清单及建议会议议程；不能把顾问推测写成客户确认的结论。

## E. 拷问卡片（按回答选择 1–3 条）

### 业务结果

- 如果管理层问“好转后具体哪里不同”，你能用客户、收入、交付周期、返工或回款中的一个变化说明吗？
- 这真是未来 3–6 个月最优先的业务结果，还是一个内部动作？
- 谁能确认当前基线，而不是凭感觉判断？

### 真实事件与流程

- 请把“协同差 / 效率低”换成最近一次事件：谁在什么时候等谁，等的是什么？
- 这一步交出去的到底是哪个信息、文件或确认？接收方是否能拒收或退回？
- 问题是一个人完成得慢，还是交接、等待、返工造成的？依据是什么？

### 部门工作

- 这个场景每周大约发生几次？谁真正做，谁最终验收？
- 它和上下游的连接在哪里？如果只改本部门，问题还会不会回到原处？
- 这是重复、繁琐、有壁垒还是高风险工作？为什么？

### 优先事项

- 高分来自真实频率和痛苦，还是因为它“听起来很适合 AI”？
- 如果三个月只能推进一项，为什么不是另一个候选项？
- 谁共同牵头，老板需要拍板的具体边界是什么？

### 方案漂移（出现平台、系统、工具、AI、开发、预算、MVP、上线等词时优先使用）

- 你给出的是实现手段，不是本次要选的工作。先不谈系统：在没有任何新工具的情况下，哪个人必须把什么信息 / 决策交给谁，才会改善业务结果？
- 这个平台或系统要替代的，究竟是哪一次重复发生的交接、判断或跟进？请把那项工作写成“起点 → 交接 → 接收方 → 结果”。
- 预算、功能、开发和上线都留到下一阶段。本次会议只需确认：这项工作是否优先、谁共同负责、先补什么流程基础。

---

## F. 提前结束与异常输入

- 用户要求提前生成：输出阶段稿，未问问题列为「待会议补充」，不假装完成。
- 用户一次给出后续题答案：归档但不要跳过当前题的拷问和完善回答。
- 用户拒绝回答：记录「未提供」，给出最小化的会议待问问题，然后继续。
- 用户要求工具 / 试点建议：简短说明本 Skill 的边界，并回到当前问题；最后在“下一阶段”列出该需求，不回答实施细节。
- 用户只回答“建平台 / 上系统 / 做 AI”：记录其为「暂存的实现手段假设」，使用“方案漂移”拷问要求改写；若完善回答仍是方案，则该题标为「待会议收敛」，不进入候选优先事项。
